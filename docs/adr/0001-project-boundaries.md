# ADR 0001: Границы проекта

- Статус: принято
- Дата: 1 октября 2026
- Участники решения: Соловцов Станислав, Псюрников Владимир, Головатенко Екатерина, Скворцов Никита

## Контекст

Команда выполняет учебный проект по курсу MLOps. На ЛР1 нужно зафиксировать, какую задачу решает проект, на каких данных, как измеряется результат и какие риски видны заранее. Эта запись нужна, чтобы все участники опирались на одинаковые границы проекта, а следующие лабораторные не меняли их молча.

## Решение

### Задача и пользователь

Проект — система рекомендаций. По истории оценок пользователя она выдаёт список из 10 объектов (например, фильмов), которые пользователь вероятнее всего оценит высоко. Пользователь результата — зритель, который выбирает, что посмотреть. Это учебный сценарий, реальных пользователей у проекта нет.

### Входные данные

Открытый набор оценок фильмов MovieLens (GroupLens), малая версия. Данные скачиваются каждым участником самостоятельно и **не добавляются в репозиторий** (папка `data/` исключена через `.gitignore`). Условия использования набора проверяются на странице набора. Закрытые наборы данных не используются.

### Метрики

- **Метрика качества:** NDCG@10 на отложенной части оценок. Она показывает, насколько высоко в списке из 10 рекомендаций стоят объекты, которые пользователь действительно оценил высоко: чем выше такие объекты, тем лучше значение.
- **Эксплуатационный показатель:** время ответа сервиса рекомендаций (95-й процентиль, p95). Целевое значение определим, когда появится сервис.

### Компоненты итогового проекта

Планируется (состав уточняется по программе курса):

- хранение и версионирование данных;
- предобработка данных;
- обучение модели с записью экспериментов;
- оценка качества модели;
- сервис с API и упаковка в контейнер;
- автоматические проверки (CI);
- мониторинг сервиса.

## Альтернативы, которые рассматривали

Альтернативы не рассматривались.

## Риски

| № | Риск | Категория | Что может случиться | Как снижаем |
|---|---|---|---|---|
| 1 | Холодный старт | Данные | Для нового пользователя без истории оценок нет данных, рекомендации будут случайными или пустыми | Заранее решить поведение для таких пользователей (например, показывать популярное) и учитывать это при оценке |
| 2 | Смещение к популярному | Данные | Модель рекомендует в основном то, что и так оценивают чаще всего, метрика выглядит хорошо, а польза мала | Смотреть не только метрику качества, но и разнообразие рекомендаций |
| 3 | Лицензия набора данных | Данные | Использование или распространение набора может нарушать его условия | Не хранить данные в репозитории, проверить условия на странице набора |
| 4 | Разные окружения у участников | Воспроизводимость | Разные версии Python и библиотек дают разные результаты или ошибки | Единая версия Python 3.12, установка по README, проверка в CI |
| 5 | Случайность в обучении и разбиении данных | Воспроизводимость | Результаты нельзя повторить, сравнение запусков теряет смысл | Фиксировать значения случайности и описывать способ разбиения данных |
| 6 | Рост времени ответа | Эксплуатация | При росте нагрузки сервис отвечает медленнее допустимого | Измерять время ответа, заложить мониторинг и проверку нагрузки |
| 7 | Падение качества со временем | Эксплуатация | Вкусы пользователей меняются, модель устаревает | Периодически пересчитывать метрики и переобучать модель |

## Отложенные решения

Команда сознательно не решает сейчас:

- какой алгоритм использовать (по сходству объектов или матричная факторизация): выбор будет сделан после предобработки данных и первых измерений;
- онлайн-дообучение модели: нужно только при реальном потоке данных;
- A/B-тестирование: нет реальных пользователей;
- feature store и оркестрация пайплайна: относятся к следующим лабораторным.

## Последствия

- Следующие лабораторные опираются на эти границы. Если границы меняются, создаётся новый ADR, а этот помечается как заменённый.
- Метрики из раздела «Метрики» используются при оценке модели и при проверке сервиса.
- Риски из таблицы пересматриваются при добавлении новых компонентов.
