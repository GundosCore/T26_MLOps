## 5. Отрицательный сценарий

Нарушение во временной копии, эталонный файл не менялся: в строке за 2026-01-10 `IsWeekend` заменён с 1 на 2.

```powershell
(Get-Content data\flights_sample.csv) -replace '^2026-01-10,10,1,','2026-01-10,10,2,' | Set-Content $env:TEMP\bad.csv
python -m mlops_team1.validate_data --data $env:TEMP\bad.csv --contract data/contract.json --report $env:TEMP\bad.json
$LASTEXITCODE
```

```text
FAIL allowed_values: 1 violation(s): IsWeekend line 7: 2 not in [0, 1]
```

Остальные девять проверок OK, код завершения `1`, в отчёте `passed: false` и `split: null`: некорректные данные не разбиваются.

## 6. Обоснование

- **Правило контракта.** `IsWeekend` допускает только 0 и 1 (`allowed_values`), потому что это признак «да/нет». Значение 2 не имеет смысла, поэтому проверка блокирующая.
- **Риск утечки.** Прогноз строится за 60 минут до планового вылета. `ArrDelay` становится известен только после прилёта, поэтому это источник цели (`ArrDelay >= 15`), а не признак. `DepHour` допустим, только если берётся из планового времени вылета: час фактического вылета уже содержит задержку. Разбиение строго по времени, без перемешивания; граница сдвигается до конца дня, чтобы один день не попал в две части и выполнялось `max(train) < min(validation)`.
- **Ограничения.** Образец — 24 строки, по одному рейсу в день, поэтому сдвиг границы на нём не проявляется, а доли опоздавших в частях сильно различаются (0.571 / 0.6 / 0.8). Нарушение порядка времени (`time_order_ok: false`) пока не делает отчёт неуспешным.
