# Момент прогноза, разбиение данных и меры против утечки (ЛР2)

Документ фиксирует, какие данные модель может видеть в момент прогноза и как набор делится на train, validation и test. Он дополняет машинный контракт `data/contract.json` и карточку набора `docs/data-card.md`.

## 1. Момент прогноза

Прогноз задержки рейса строится **за 60 минут до планового отправления**. Модели можно давать только то, что гарантированно известно к этому моменту. Всё, что появляется позже (фактический вылет, фактическое прибытие, задержки), использовать как признак запрещено.

Цель: рейс задержан, если `ArrDelay >= 15` (опоздание прибытия на 15 минут и больше).

## 2. Поля набора и их доступность

| Поле | Роль в контракте | Когда становится известно | Можно как признак? | Почему |
|---|---|---|---|---|
| `FlightDate` | `event_time` | заранее, из расписания | да, и это ключ разбиения по времени | дата рейса известна при составлении расписания |
| `DepHour` | `feature` | заранее, из расписания | да, при условии ниже | плановый час вылета известен заранее |
| `IsWeekend` | `feature` | заранее, по календарю | да | выходной или нет, определяется по дате |
| `ArrDelay` | `target_source` | **после прилёта** | **нет** | это и есть ответ; используется только для построения цели |

Условие для `DepHour`: час берётся из **планового** времени отправления. Если вычислять его из фактического времени вылета, признак будет содержать информацию о задержке, и это утечка.

Если в данные будут добавлены новые поля, каждое проходит ту же проверку: известно ли оно за 60 минут до планового вылета. Например, поля реального набора BTS о фактическом вылете (`DepDelay`, `DepTime`, `TaxiOut`, `WheelsOff`), фактическом прибытии (`ArrTime`, `TaxiIn`), причинах задержки (`CarrierDelay`, `WeatherDelay` и т.п.), отмене (`Cancelled`) и уходе на запасной аэродром (`Diverted`) появляются после момента прогноза, поэтому как признаки не допускаются.

## 3. Разбиение на train, validation и test

Данные сортируются по `FlightDate` (контракт требует возрастающего порядка) и делятся на три последовательных периода в пропорции 60/20/20. Перемешивание и случайная стратификация запрещены.

Разбиение считает функция `split_summary` в `src/mlops_team1/validate_data.py`, результат записывается в отчёт валидации (`reports/validation/lr2.json`, блок `split`):

1. строки сортируются по `FlightDate`;
2. границы ставятся на позициях `int(0,6 · n)` и `int(0,8 · n)`;
3. если граница попала внутрь дня (дата до и после неё одинаковая), она сдвигается вперёд до конца этого дня, чтобы один день не оказался в двух частях;
4. для каждой части считаются число строк, первая и последняя дата и доля `ArrDelay >= 15`;
5. проверяется порядок `max(train) < min(validation) <= max(validation) < min(test)` (поле `time_order_ok`).

Если данные не прошли проверки контракта, блок `split` в отчёте равен `null`: разбивать некорректные данные нельзя.

- **train** — самый ранний период: на нём обучаются модель и все преобразования;
- **validation** — следующий период: на нём выбираются модель и порог;
- **test** — самый поздний период: используется один раз, для итоговой оценки.

Границы для образца `data/flights_sample.csv` (24 строки, по одному рейсу в день, поэтому сдвиг не нужен: `int(24 · 0,6) = 14`, `int(24 · 0,8) = 19`). Числа взяты из блока `split` отчёта валидации:

| Часть | Строк | Период | `ArrDelay >= 15` |
|---|---|---|---|
| train | 14 | 2026-01-05 … 2026-01-18 | 8 из 14 (57,1%) |
| validation | 5 | 2026-01-19 … 2026-01-23 | 3 из 5 (60,0%) |
| test | 5 | 2026-01-24 … 2026-01-28 | 4 из 5 (80,0%) |

Проверка порядка: `max(train) = 2026-01-18 < min(validation) = 2026-01-19 <= max(validation) = 2026-01-23 < min(test) = 2026-01-24`. Условие выполнено, в отчёте `time_order_ok: true`.

Доли задержанных рейсов в частях заметно различаются. На 24 строках это нормально: образец нужен для проверки инфраструктуры, а не для выводов о качестве модели.

### Правило для полного набора

В реальных данных за один день много рейсов. Если резать строго по номеру строки, один и тот же день может оказаться и в train, и в validation, и тогда условие `max(train) < min(validation)` нарушится. Поэтому граница сдвигается до конца дня (шаг 3 выше): все рейсы одного дня попадают в одну часть. Из-за сдвига доли частей на полном наборе могут немного отличаться от 60/20/20. Для полного набора календарные границы, число строк и доля задержек берутся из блока `split` отчёта.

## 4. Меры против утечки

1. `ArrDelay` используется только для построения цели и не входит в список признаков модели.
2. Разбиение только по времени, без перемешивания.
3. Нормализация, словари категорий и заполнение пропусков обучаются только на train и затем применяются к validation и test.
4. Признаки-агрегаты (например, средняя задержка по маршруту) считаются только по рейсам, которые завершились до момента прогноза, а не по всему набору.
5. Модель и порог выбираются по validation; test открывается один раз для итоговой оценки.

## 5. Что проверяется автоматически

- Валидатор проверяет, что `FlightDate` идёт в возрастающем порядке (проверка `sorted`), и что `ArrDelay` имеет допустимый диапазон.
- В отчёт валидации записывается блок `split`: границы периодов, число строк, доля задержек и результат проверки порядка времени.
- Тест `test_report_contains_split` в `tests/test_data_contract.py` проверяет на образце размеры 14/5/5, долю задержек в train 0,571 и `time_order_ok: true`.
