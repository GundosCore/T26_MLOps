# Решение: версия данных v2

- Статус: принято
- Автор: Скворцов Никита (`snikersito`), роль Data version owner
- Затрагивает: `data/flights_sample.csv` (под DVC), контракт `data/contract.json` 2.0.0

## 1. Причина

Для ЛР3 нужно показать, как набор данных получает новую версию и как это отражается на воспроизводимости и разбиении. Реальных новых данных у команды нет, поэтому v2 — синтетическое продолжение учебного образца v1. Преподаватель разрешил составить его самостоятельно. Чтобы версию можно было пересоздать байт в байт, строки создаёт скрипт с фиксированным seed, а не человек вручную.

## 2. Источник строк

- Скрипт: `src/mlops_team1/generate_v2.py` (только стандартная библиотека).
- Вход: v1 (`tests/fixtures/flights_sample_v1.csv`, 24 строки, SHA-256 `d2038bfd4ba28a304e1bed26578c9bfcb556942b51694b8342a75f4f2dbf617e`).
- Параметры: `--days 16 --seed 2026`.
- Как устроен:
  - `read_base` читает v1 и проверяет заголовок `FlightDate,DepHour,IsWeekend,ArrDelay`;
  - `make_rows` добавляет по одной строке на каждый следующий день после последней даты v1; `DepHour` случайный 5–21, `ArrDelay` случайный 4–45, `IsWeekend` вычисляется по дате (суббота и воскресенье = 1);
  - `main` записывает заголовок, строки v1 без изменений и новые строки.
- `random.Random(seed)` — отдельный генератор с фиксированным seed: одинаковый seed даёт одинаковую последовательность чисел, поэтому одинаковые байты файла.
- `lineterminator="\n"` — переносы строк LF на любой ОС; без этого на Windows были бы CRLF и другой SHA-256 (такая проблема уже была в ЛР2).
- Строки составлены командой по образцу v1. Реальных рейсов в них нет.

## 3. Изменение периода

| | Строк | Период |
|---|---|---|
| v1 | 24 | 2026-01-05 … 2026-01-28 |
| v2 | 40 | 2026-01-05 … 2026-02-13 |

Добавлены 16 дат: 2026-01-29 … 2026-02-13, по одной строке на день. Первые 24 строки v2 совпадают с v1. `git diff --no-index --stat` между версиями: `16 insertions(+)`, удалений и изменений нет.

## 4. Влияние на разбиение

Границы считаются по числу строк: `int(0.6 · n)` и `int(0.8 · n)` (функция `split_summary`). Значения v2 взяты из отчёта валидатора.

| Часть | v1: строк | v1: период | v1: доля `ArrDelay >= 15` | v2: строк | v2: период | v2: доля `ArrDelay >= 15` |
|---|---|---|---|---|---|---|
| train | 14 | 2026-01-05 … 01-18 | 0.571 | 24 | 2026-01-05 … 01-28 | 0.625 |
| validation | 5 | 2026-01-19 … 01-23 | 0.6 | 8 | 2026-01-29 … 02-05 | 0.875 |
| test | 5 | 2026-01-24 … 01-28 | 0.8 | 8 | 2026-02-06 … 02-13 | 0.75 |

`time_order_ok: true` в обеих версиях.

Вывод: в v2 весь v1 уходит в train, включая бывшие validation и test, а новые validation и test состоят только из новых дней. Это осознанное решение: границы зависят от числа строк, и при росте набора test всегда остаётся самым поздним периодом. Метрики, посчитанные на v1 и на v2, сравнивать напрямую нельзя: это разные test-периоды. Сама v1 не меняется: её байты и хеш закреплены в DVC и в `tests/fixtures`, поэтому откатывать или переписывать её задним числом не нужно, к ней всегда можно вернуться.

## 5. Ограничения

- Данные синтетические. `ArrDelay` и `DepHour` генерируются случайно и независимо, связи между признаками и целью нет по построению. На v2 нельзя делать выводы о качестве модели.
- Доли опоздавших в частях (0.625 / 0.875 / 0.75) — следствие случайных чисел, а не свойство рейсов.
- Детерминизм гарантирован для одной и той же версии Python: `random.Random` в CPython стабилен между версиями, но смена seed, числа дней или файла v1 даёт другой файл и другой хеш.

## 6. Как воспроизвести

```powershell
python -m mlops_team1.generate_v2 --base tests/fixtures/flights_sample_v1.csv --out $env:TEMP\v2.csv --days 16 --seed 2026
Get-FileHash $env:TEMP\v2.csv -Algorithm SHA256
python -m mlops_team1.validate_data --data $env:TEMP\v2.csv --contract data/contract.json --report $env:TEMP\v2-check.json
```

Ожидается:

- SHA-256 v2: `bf35cf01db04fb31de810dc16009d643e6bf3be22c791faea7c00fdbc25cff08`, размер 780 байт;
- валидатор: код 0, `rows: 40`, split 24/8/8, `time_order_ok: true`;
- тесты генератора: `python -m pytest -q tests/test_generate_v2.py` (6 тестов: одинаковый seed → одинаковые байты, другой seed → другие строки, v1 сохранён как начало файла, даты и выходные продолжаются верно, только LF, v2 проходит контракт).
