# Совместимость изменений API (ЛР7)

Контракт сервиса версии 0.3.0: `POST /predict` принимает `dep_hour` (0–23) и `is_weekend` (0 или 1), отвечает полями `delay_probability`, `delayed`, `threshold`, `model_version`, `request_id`. Ошибки 422, 503 и 404 имеют форму `ErrorResponse`.

Изменение совместимо, если клиенты продолжают работать без правок. То, что сервер запускается и тесты зелёные, ещё не значит, что изменение безопасно. Поэтому в таблице у каждого изменения указано, что произойдёт с клиентом.

Клиенты, о которых идёт речь (предположение: других у сервиса пока нет):

- любой вызывающий сервис, который отправляет `dep_hour` и `is_weekend`, читает `delay_probability`, `delayed`, `threshold` и использует `request_id` для поиска в логах;
- наш `scripts/api_contract_smoke.py`: он строгий клиент, проверяет точный набор полей ответа.

## Изменения из задания, разобранные на нашем API

| № | Изменение | Совместимо? | Что случится с клиентом | Действие | Что покажет проверка |
|---|---|---|---|---|---|
| 1 | Добавить необязательное поле в ответ (например, `model_name`) | Да, если клиент игнорирует неизвестные поля. Для строгого клиента (наш smoke, тесты на точный набор полей) нет | Обычный клиент не заметит. Строгий упадёт на «лишнем» поле | Обновить схему OpenAPI, тесты и smoke, предупредить владельцев строгих клиентов | `tests/test_api.py::test_predict_contract` сравнивает точный набор полей ответа и упадёт |
| 2 | Удалить поле ответа (например, `threshold`) | Нет | Клиент, который читает `threshold`, получит ошибку при разборе ответа | Новая версия API или период миграции, в котором поле ещё возвращается | `tests/test_api.py::test_predict_contract` |
| 3 | Сузить допустимый диапазон (например, `dep_hour` только 5–22) | Нет для прежних клиентов | Запросы с часами 0–4 и 23, которые раньше работали, получат 422 | Согласовать переход с владельцами клиентов, сообщить новый диапазон заранее | `tests/test_api.py::test_predict_rejects_invalid_payload[hour-24]` показывает, как выглядит отказ по диапазону |
| 4 | Добавить обязательное поле запроса (например, `carrier`) | Нет | Все существующие запросы получат 422 (поле отсутствует) | Версионирование контракта и период миграции: сначала поле необязательное, потом обязательное | `tests/test_api.py::test_predict_rejects_invalid_payload[missing-field]` |
| 5 | Добавить новый endpoint (например, `GET /version`) | Да | Существующие клиенты его не вызывают и не замечают | Документировать, заново экспортировать схему `reports/openapi/lr7-openapi.json`: сохранённая схема устареет | Тест `tests/test_api.py::test_openapi_describes_predict` проверяет только наличие путей `/healthz`, `/readyz`, `/predict` и новый endpoint не заметит. Заметит только сравнение сохранённой схемы со схемой из кода |
| 6 | Изменить смысл существующего поля (например, `delay_probability` станет минутами задержки) | Нет, и это самый опасный случай | Тип остаётся числом, сервис работает, но клиент принимает решения по неверным числам. Ограничение `[0, 1]` в `PredictionResponse` не даст вернуть минуты: сервис начнёт отвечать 500 | Новое имя поля или новая версия API, старое поле не переиспользовать | Проверка диапазона ответа в `PredictionResponse`; тест типов смысл не заметит |

## Изменения, сделанные в самой ЛР7

| № | Изменение | Совместимо? | Что случится с клиентом | Действие |
|---|---|---|---|---|
| 7 | `X-Request-ID` принимается только из символов `A–Z`, `a–z`, `0–9`, `.`, `_`, `:`, `-` длиной до 128; иначе сервис выдаёт новый UUID | Да для клиентов с такими идентификаторами. Нет для клиентов, которые отправляли идентификаторы с пробелами, `/` или другими символами | Раньше такой идентификатор возвращался как есть, теперь возвращается UUID, и клиент не найдёт свой запрос в логах по своему идентификатору | Сообщить правило клиентам, идентификаторы из безопасного набора символов не менять |
| 8 | Повреждённый файл модели останавливает запуск, раньше сервис стартовал и отвечал 503 | Формат HTTP-ответов не изменился, при отсутствии файла по-прежнему 503. Изменилось поведение при поломке модели | Вместо 503 с `error_code` `not_ready` клиент получает отказ соединения, пока контейнер не исправят | Согласовать с теми, кто эксплуатирует сервис: мониторинг должен смотреть на состояние контейнера, а не только на 503 |
| 9 | Ограничения в `PredictionResponse`: вероятность и порог в `[0, 1]`, `model_version` и `request_id` непустые | Да | Допустимые значения те же, что возвращал сервис раньше. В схеме появились `minimum`, `maximum` и `minLength` | Обновить схему OpenAPI |
| 10 | `info.version` в OpenAPI стала `0.3.0` (в ЛР6 была `1.0.0`) | Поведение не меняется | Номер уменьшился: клиент, который сравнивает версии, сочтёт сервис более старым | Версия 0.3.0 требуется заданием ЛР7. Клиентам сообщить, что нумерация контракта начата заново |

## Как классифицировать следующее изменение

1. Выписать, какие поля запроса и ответа оно затрагивает.
2. Для каждого клиента ответить, что он делает с этим полем сейчас и что произойдёт после изменения.
3. Если хоть один клиент сломается, изменение несовместимо: нужна новая версия или период миграции.
4. Проверить, что изменение видно в схеме OpenAPI и ловится тестом контракта.
