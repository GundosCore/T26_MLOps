# Правила работы команды

Эти правила описывают, как команда 1 работает с репозиторием в ЛР1. Если правило нарушено, об этом нужно сказать тимлиду до слияния.

## 1. Схема работы

1. Тимлид (Станислав, `@GundosCore`) ведёт общий репозиторий `GundosCore/T26_MLOps`. В нём есть ветка `main` и по одной именной ветке на каждого участника: `psyurnikov`, `golovatenko`, `skvortsov`.
2. Каждый участник делает форк репозитория тимлида и работает в ветке `main` **своего** форка.
3. Когда работа готова, участник открывает pull request (PR) из `main` своего форка в **свою именную ветку** в репозитории тимлида.
4. Тимлид проверяет PR и сливает его. Затем тимлид открывает PR из именной ветки в `main` репозитория тимлида и сливает его после зелёной проверки CI.
5. Готовую работу тимлид отправляет pull request'ом в ветку команды в репозитории преподавателя. Участники в репозиторий преподавателя ничего не отправляют.
6. Ссылки на PR участники прикрепляют в системе SKIF.

## 2. Ветки

- Участники работают в `main` своего форка.
- Тимлид для отдельных задач использует ветки формата `<тип>/issue-<номер>-<краткое-название>`, например `docs/issue-1-readme`.
- Перед началом новой работы участник синхронизирует форк: кнопка Sync fork → Update branch на GitHub и Pull в GitHub Desktop.

## 3. Коммиты

- Формат сообщения: `<тип>: <описание>`.
- Типы: `docs` (документация), `test` (тесты), `chore` (служебные изменения), `fix` (исправление ошибки).
- В коммит попадают только файлы, относящиеся к задаче. Файлы выбираются вручную, а не командой «добавить всё».

## 4. Pull request

В каждом PR должны быть:

- ссылка на issue (`Closes #<номер>`);
- краткое описание сделанного;
- способ проверки (какие команды выполнить и какой результат ожидается);
- ссылка на реальный зелёный запуск CI;
- назначенный reviewer, который не является автором.

Перед созданием PR нужно проверить в окне создания, что **base repository** и **base** выбраны верно (репозиторий тимлида и именная ветка участника).

## 5. Review

- Автор не одобряет свой PR.
- Review должно быть содержательным: прочитать весь diff, запустить команды или проверить зелёный CI, оставить комментарий о том, что именно проверено. Комментарий «ок» без проверки не принимается.
- Каждый участник оставляет review хотя бы на одну чужую работу.

## 6. Проверки перед push

Перед каждым push выполняется:

```
python -m ruff check .
python -m pytest -q
```

Причина: проверки CI одинаковые. Был случай, когда после правки форматирования в тестовом файле исчезли пустые строки, и CI упал на правиле сортировки импортов.

## 7. Что нельзя коммитить

- виртуальное окружение (`.venv`);
- файлы с переменными окружения (`.env`) и любые пароли, токены, ключи;
- данные и обученные модели;
- временные файлы и кэши.

## 8. Защита ветки `main`

Тимлид настраивает правила для `main`: изменения только через PR, минимум одно одобрение, обязательная проверка CI, запрет принудительной перезаписи истории и удаления ветки. Если какое-то из правил недоступно на тарифе GitHub, команда соблюдает его вручную: PR обязателен, review обязательно, зелёный CI проверяется перед слиянием.
